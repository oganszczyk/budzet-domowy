1. Cel dokumentu

Dokument opisuje pierwszą wersję aplikacji mobilnej do rejestrowania, kontrolowania, kategoryzowania i analizowania

wydatków domowych. Ma być bezpośrednią instrukcją dla agenta AI tworzącego kod, dlatego rozdziela wymagania na

funkcje, reguły biznesowe, dane, ekrany, etapy wykonania i kryteria akceptacji.

Najważniejsza zasada wdrożenia

Agent powinien budować aplikację etapami. Po każdym etapie aplikacja ma się uruchamiać, kompilować i zachowywać

istniejące dane. Nie należy wdrażać wszystkich modułów jednocześnie.

1.1. Jak czytać checklistę

1.2. Instrukcja dla agenta AI

[ ] P0 Przed rozpoczęciem etapu utworzyć krótką listę plików, które będą dodane lub zmienione.

[ ] P0 Nie usuwać działających funkcji podczas dodawania kolejnego modułu.

[ ] P0 Po każdym etapie uruchomić analizę kodu, kompilację i test podstawowego przepływu użytkownika.

[ ] P0 Stosować migracje bazy danych zamiast kasowania lokalnej bazy przy zmianach schematu.

[ ] P0 Kwoty przechowywać jako całkowitą liczbę groszy, np. 125,50 zł jako 12550.

[ ] P0 Nazwy klas i zmiennych mogą być angielskie, ale cały interfejs użytkownika ma być po polsku.

2. Wizja produktu

Wizja

Jedna prosta aplikacja na telefon, która pokazuje, ile pieniędzy zostało wydane w danym miesiącu na rachunki domowe,

subskrypcje oraz pozostałe zakupy, a także pozwala szybko dodać wydatek ręcznie lub poprzez skan paragonu.

2.1. Problem użytkownika

- Rachunki, subskrypcje i zakupy są obecnie rozproszone i trudne do porównania.

- Koszty cykliczne łatwo przeoczyć lub opłacać bez kontroli ich łącznej wartości.

- Ręczne przepisywanie danych z paragonów jest czasochłonne.

- Brakuje jednego miesięcznego podsumowania wszystkich wydatków.

2.2. Docelowy efekt MVP

[x] Po otwarciu aplikacji użytkownik od razu widzi bieżący miesiąc i trzy główne sumy.

[x] Rachunki tworzą się co miesiąc jako pozycje oczekujące na kwotę i opłacenie.

[x] Subskrypcje przenoszą się automatycznie na kolejne okresy.

[x] Zakup można dodać ręcznie albo zeskanować paragon i potwierdzić sklep, datę i kwotę.

[x] Każda zapisana płatność trafia do jednej chronologicznej historii.

5.6. Skanowanie paragonu - uproszczone OCR

Zakres OCR w MVP

Jeden paragon jest zapisywany jako jedna transakcja. System odczytuje wyłącznie nazwę sklepu, datę i końcową kwotę.

Nie odczytuje listy produktów ani ich kategorii.

Przepływ użytkownika

[ ] P0 1. Użytkownik wybiera „Zeskanuj paragon”.

[ ] P0 2. Aplikacja prosi o dostęp do aparatu lub pozwala wybrać zdjęcie z galerii.

[ ] P0 3. Użytkownik wykonuje zdjęcie.

[ ] P0 4. Aplikacja uruchamia OCR i wyświetla ekran weryfikacji.

[ ] P0 5. Pola sklep, data i kwota są wstępnie uzupełnione, jeżeli zostały rozpoznane.

[ ] P0 6. Użytkownik wybiera podkategorię zakupu.

[ ] P0 7. Aplikacja pyta: „Czy dane zostały poprawnie odczytane?”.

[ ] P0 8. Użytkownik zapisuje, poprawia dane, ponawia zdjęcie lub anuluje.

Reguły rozpoznawania

[ ] P0 Kwoty oznaczone jako „SUMA”, „RAZEM”, „DO ZAPŁATY” lub podobne mają wyższy priorytet niż sumy częściowe.

[ ] P0 Gdy znaleziono kilka możliwych kwot, wybrać najbardziej prawdopodobną, ale zawsze umożliwić zmianę.

[ ] P0 Data musi być prawidłową datą kalendarzową; w razie braku pozostawić pole puste lub użyć bieżącej daty z wyraźnym

oznaczeniem do sprawdzenia.

[ ] P0 Nazwa sklepu jest sugestią i może pozostać pusta.

[ ] P0 Zdjęcie paragonu może zostać zapisane lokalnie jako opcjonalny załącznik.

[ ] P0 Nigdy nie zapisywać wyniku OCR automatycznie bez potwierdzenia użytkownika.

Stany błędów

[ ] P1 Brak uprawnień do aparatu - wyjaśnić problem i zaoferować otwarcie ustawień lub wybór zdjęcia.

[ ] P1 Nieczytelne zdjęcie - pokazać możliwość ponowienia skanu.

[ ] P1 Brak rozpoznanej kwoty - pole kwoty puste i wymagane do ręcznego uzupełnienia.

[ ] P1 Błąd OCR - użytkownik nadal może przejść do formularza ręcznego z zachowanym zdjęciem.

AC - kryteria akceptacji

[ ] Skan nie tworzy transakcji przed naciśnięciem „Zapisz”.

[ ] Każde rozpoznane pole można edytować.

[ ] Po zapisaniu transakcja ma źródło RECEIPT_SCAN i jest widoczna w historii.

[ ] W przypadku pustej kwoty zapis jest zablokowany do czasu jej uzupełnienia.
